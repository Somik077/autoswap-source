## Механика свапа: проверено по байткоду 1.21.11

Мод **не эмулирует мышь** и **не собирает пакеты вручную**. Он вызывает ванильный
`ClientPlayerInteractionManager.clickSlot(syncId, slot, button, SlotActionType, player)`
(в 26.1 — `gameMode.handleContainerInput`), который:
1. выходит, если `syncId != player.currentScreenHandler.syncId` (лог `Ignoring click in
   mismatching container`);
2. применяет клик локально — `ScreenHandler.onSlotClick(...)` (предсказание), это идёт ПЕРВЫМ;
3. собирает список изменённых слотов;
4. `new ClickSlotC2SPacket(syncId, revision, slot, button, actionType, modifiedStacks, cursor)`,
   где `revision` берётся из `ScreenHandler.getRevision()`;
5. `ClientPlayNetworkHandler.sendPacket(...)`.

Пакеты за свап (текущий код): 1 клик для левой руки (`SWAP`, button 40) или 2–3 клика
(`PICKUP`: src → dst → обратно src), плюс `CloseHandledScreenC2SPacket(0)` от закрытия экрана.
Открытие своего инвентаря пакета не шлёт. HUD и опрос клавиши — чисто клиентские.

**Главное открытие (важно для дизайна):** `MinecraftClient` вызывает `handleInputEvents()` только
при `currentScreen == null` (проверено байткодом: `ifnonnull` по `currentScreen` перед вызовом).
Значит открытый экран **останавливает игрока** — как и происходит у человека, который лезет в
инвентарь. Вариант **без экрана** (моя антидетект-правка) шлёт клики, продолжая бежать на полной
скорости, и это самый сильный признак для античита: человек так не может. То есть открытие экрана —
не косметика, а функциональная маскировка движения. Вывод: правильный вариант — экран оставить,
а вместо него чинить `revision` (ждать `getRevision() != rev`) и не ставить кулдаун в 0.

## НАЙДЕНА ПРИЧИНА КИКА: Grim MultiActionsC / MultiActionsD

Античит на Space Times — форк **`KaelusAI/GroundedGrim`** (ветка `2.0`), это форк `GrimAnticheat/Grim`.
Проверки лежат в `common/src/main/java/ac/grim/grimac/checks/impl/multiactions/` (A–G), читаются
напрямую с raw.githubusercontent.com. Нас касаются две, и обе **не experimental**, то есть боевые:

**MultiActionsC** — `grim.multiactions.inventory_click_while_moving`, «Clicked in inventory while moving»:
```java
if (event.getPacketType() != PacketType.Play.Client.CLICK_WINDOW) return;
if (player.serverOpenedInventoryThisTick) return;
boolean sprinting = player.isSprinting && ...;
boolean sneaking  = player.isSneaking && (version < 1.15 || version >= 1.21.9);
boolean input     = player.supportsEndTick() && player.packetStateData.knownInput.moving();
if (!sprinting && !sneaking && !input) return;
flag(...); event.setCancelled(true);      // клик отменяется, игроку кик
```

**MultiActionsD** — то же самое для `CLOSE_WINDOW` («Closed inventory while moving»), пакет не
отменяет, но флажит.

То есть проверка ловит **клик по слоту и закрытие экрана в момент, когда клиент сообщил серверу,
что игрок движется/спринтует/крадётся**.

**Почему ваниль её не задевает** (проверено байткодом 1.21.11):
`MinecraftClient.setScreen` вызывает `KeyBinding.unpressAll()` → все клавиши движения отпускаются →
`KeyboardInput.tick()` (вызывается каждый тик из `ClientPlayerEntity.tickMovement()`, читает
`settings.forwardKey.isPressed()` и т.д.) собирает нейтральный `PlayerInput` → `ClientPlayerEntity`
шлёт `PlayerInputC2SPacket` со всеми false → сервер видит `knownInput.moving() == false`.
`Input.playerInput` — **публичное поле**, им можно управлять напрямую.

**Выводы:**
1. Моя антидетект-правка (убрать экран) для Grim **вредна**: клики уходят, пока игрок держит W →
   MultiActionsC флажит каждый клик. Открытие экрана — не косметика, а именно то, что отпускает ввод.
2. Переписанная версия Somik (открывать экран) — **правильное направление**, и теперь понятно, почему.
3. wexside экран не открывает → на Grim-сервере он бы тоже флажился. Как эталон он не годится.
4. Старый оригинал делал `player.setSprinting(false)` до и восстанавливал после — это была защита
   от спринт-ветки проверки. **Я её вырезал, и это была регрессия.**
5. `inventoryOpenDelayTicks = 1` + `swapCooldownMs = 0` в конфиге Somik — гонка: клик уходит почти
   сразу после открытия экрана, сервер мог ещё не получить нейтральный input. Нужно ≥2–3 тика.

**Диагностика на будущее:** если кикает сразу на первом клике — это C (клик при движении);
если только после завершения свапа — D (закрытие при движении).

### Как это решает wexside (важно для дизайна)

`mixin/KeyboardMovementMixin.java` — `@Mixin(Input.class)`, инжект в `tick` на TAIL, переписывает
`playerInput` и `movementVector`. То есть у них есть **подмена состояния ввода** (silent movement),
через которую можно отправить серверу `moving = false`, не открывая экран и не останавливая игрока.
Для свапа они это **не используют**: `AutoSwapModule` → `InventoryController` → `clickSlot`, экран
не открывается, `CloseHandledScreenC2SPacket` для своего инвентаря не шлётся. То есть по проблеме
движения их автосвап ничего не делает — как эталон антидетекта он не годится, но как эталон
функционала (сравнение по NBT, мешки, селектор, очередь задач с приоритетами) — вполне.
Полезный вывод: у нас есть третий вариант правки — не открывать экран, а подменять
`player.input.playerInput` (поле публичное) на время клика.

## Грабли миксинов: сборка зелёная, а игра падает (коммиты `cb4be54` → `b677652`)

**Первая попытка миксина уронила игру при заходе в мир** — «ошибка сетевого протокола», а на
самом деле `MixinApplyError`:

```
Mixin apply failed autoswap.mixins.json:KeyboardInputMixin -> net.minecraft.client.input.KeyboardInput:
@Shadow field playerInput was not located in the target class KeyboardInput
```

Причина: `playerInput` объявлено в `Input`, а `@Shadow` ищет поле **только в самом целевом классе**,
наследство он не разворачивает. Лечение — accessor-миксин на классе, где поле реально объявлено:

```java
@Mixin(Input.class)
public interface InputAccessor {
    @Accessor("playerInput")      void setPlayerInput(PlayerInput input);
    @Accessor("movementVector")   void setMovementVector(Vec2f vec);
}
```
а в `KeyboardInputMixin` писать через него: `((InputAccessor) (Object) this).setPlayerInput(...)`.

**Побочная польза:** падение доказало, что живой класс ввода — **`KeyboardInput`**, а не `Input`.
Базовый `Input.tick()` вообще пустой (`0: return`), и `KeyboardInput.tick()` его не вызывает —
поэтому миксин на `Input` бесполезен, нужен на `KeyboardInput`.

**Главный урок: `./gradlew build` НЕ проверяет миксин.** Сборка была зелёной в обоих случаях —
и с рабочим, и с падающим миксином. Проверять только запуском (`runClient`) и грепать лог на
`Mixin apply.*failed`. Refmap современному Loom не нужен — ремап проверяется тем, что в jar-е
класс ссылается на `class_XXXX` (у нас `class_10185.field_54155`, `class_241.field_1340`).

## Скорость свапа: 8 тиков → 1–2 (коммит `b677652`)

Somik сказал, что свап медленнее ручного — замирание было ~400 мс. Что сделано:

- экран открывается прямо в `schedule()`, а не на следующем тике;
- `startPair` больше не возвращает управление, а проваливается в первый клик в том же вызове;
- состояние `CLOSING` убрано, экран закрывается сразу после последнего клика;
- `MIN_STEP_DELAY = 1`, дефолт `stepDelayTicks` 3 → 1.

Итого: тик N — нажатие + открытие экрана, тик N+1 — клик и закрытие. Ввод к моменту клика уже
нейтральный, потому что `KeyboardInput.tick()` идёт во время тика игрока, то есть **до**
`END_CLIENT_TICK`, где мод и кликает.




### Уточнение: `unpressAll` вызывается только при ОТКРЫТИИ экрана

Байткод `MinecraftClient.setScreen` (1.21.11):
```
158: putfield currentScreen = screen
177: aload_1; ifnull 217          // if (screen != null) { ... } else { ... }
181: mouse.unlockCursor()
188: KeyBinding.unpressAll()      ← ВНУТРИ ветки screen != null
191: screen.init(width, height)
217: (else: screen == null → lockCursor, без unpressAll)
```
Значит клавиши отпускаются **при открытии** экрана, а не при закрытии, и на протяжении всего свапа
ввод остаётся нейтральным. Это ровно то, чего требует MultiActionsC/D.

Симптом Somik: кикнуло «где-то после закрытия» → похоже на **MultiActionsD** (`CLOSE_WINDOW`).
Из кода проверки кик при закрытии не объясняется однозначно: закрытие идёт в том же тике, что и
последний клик, а при кулдауне 0 и частых свапах игрок между свапами успевает снова нажать W.
Разбираться надо замером, а не рассуждением: добавить в мод отладочный лог состояния
(`player.input.playerInput`, `isSprinting()`, `isSneaking()`) в момент клика и в момент закрытия —
и посмотреть его лог после одного теста на сервере.
